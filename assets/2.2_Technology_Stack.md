# 2.2 Technology Stack

## Purpose

This document defines the technology stack for **Nexora — AI Stock Decision Support & Prediction Tool**.

It covers the complete scope defined by the Master Checklist:

```text
Frontend
Backend
ML / Data
Storage
```

This document records finalized technology decisions as well as technology areas that require decisions in later implementation phases.

> **Important:** This is a technology-definition and documentation phase. It establishes the technology foundation and decision criteria; it does not require implementation of every technology listed here.

---

# Frontend

The frontend provides the user-facing application through which users search for stocks, provide analysis preferences, request predictions, view results, manage watchlists, and review prediction history.

## Technology Decisions

- [x] Framework/library — React + TypeScript.
- [x] Build tool — Vite.
- [x] Routing — React Router.
- [x] State management — React Context + hooks initially.
- [x] Charting library — Recharts.
- [x] UI/icon system — Lucide React + custom Nexora UI components.
- [x] Styling strategy — CSS Modules + global CSS/design tokens.

## 1. Framework / Library

**Decision:** React + TypeScript.

### Why

React provides the component-based frontend architecture required for Nexora, while TypeScript provides static typing and helps maintain a larger frontend codebase.

### Current Position

Finalized.

---

## 2. Build Tool

**Decision:** Vite.

### Why

Vite provides a lightweight development server and production build workflow suitable for the Nexora React application.

### Current Position

Finalized.

---

## 3. Routing

**Decision:** React Router.

### Why

Nexora will contain multiple application areas such as stock search, analysis/prediction workflows, results, watchlist, and history. Client-side routing provides structured navigation between these areas.

### Current Position

Finalized.

---

## 4. State Management

**Decision:** React Context + hooks initially.

### Why

The current application scope does not justify introducing a heavier state-management framework at the foundation stage.

Context and hooks can handle shared application state initially while keeping the architecture simple.

### Future Consideration

A dedicated state-management solution can be introduced later if application complexity requires it.

### Current Position

Finalized for the initial implementation.

---

## 5. Charting Library

**Decision:** Recharts.

### Intended Use

Recharts will support visual presentation of relevant stock-analysis and prediction information.

Potential uses include:

- Historical price visualization.
- Analytical indicators.
- Prediction-related visualizations.
- Risk/confidence visualization.
- Other result-oriented charts.

### Current Position

Finalized.

---

## 6. UI / Icon System

**Decision:** Lucide React + custom Nexora UI components.

### Why

Lucide React provides a consistent icon system while custom Nexora components allow the project to maintain its own visual language and reusable interface patterns.

### Current Position

Finalized.

---

## 7. Styling Strategy

**Decision:** CSS Modules + global CSS/design tokens.

### Why

CSS Modules provide component-level style isolation while global CSS/design tokens provide consistency for shared values such as typography, spacing, layout, and visual design rules.

### Current Position

Finalized.

---

# Backend

The backend provides the application/API layer between the frontend and the market-data, processing, ML, risk, decision, and storage components.

## Technology Decisions

- [x] Language — Python.
- [x] API framework — FastAPI.
- [x] Validation — Pydantic.
- [x] API documentation — OpenAPI + Swagger UI + ReDoc.
- [x] Logging — Python `logging`.
- [x] Configuration management — Environment variables + `.env` + `python-dotenv`.

## 1. Language

**Decision:** Python.

### Why

Python is used for the backend because it integrates naturally with the project's ML/data ecosystem and provides the required application and API capabilities.

### Current Position

Finalized.

---

## 2. API Framework

**Decision:** FastAPI.

### Why

FastAPI provides the API foundation required to expose Nexora's application services and prediction workflows.

It also integrates well with Pydantic validation and automatic API documentation.

### Current Position

Finalized.

---

## 3. Validation

**Decision:** Pydantic.

### Intended Use

Pydantic will be used for structured request/response validation and typed API schemas.

### Current Position

Finalized.

---

## 4. API Documentation

**Decision:** OpenAPI + Swagger UI + ReDoc.

### Intended Use

The API documentation layer will provide:

- Machine-readable API specifications.
- Interactive API documentation.
- Developer-facing API reference.

### Current Position

Finalized.

---

## 5. Logging

**Decision:** Python `logging`.

### Intended Use

Logging will support:

- Application events.
- API activity.
- Validation failures.
- Processing failures.
- Prediction-related errors.
- Unexpected exceptions.
- Important system events.

Sensitive information and secrets must not be written to logs.

### Current Position

Finalized.

---

## 6. Configuration Management

**Decision:** Environment variables + `.env` + `python-dotenv`.

### Intended Use

Configuration values that differ between environments should be managed outside application source code.

The repository provides:

```text
.env.example
```

Actual `.env` files containing secrets must remain local and ignored by Git.

### Current Position

Finalized.

---

# ML / Data

The ML/Data layer covers the development environment, data-processing technologies, ML libraries, model storage/versioning, and optional experiment tracking.

## Technology Decisions

- [x] Python environment — separate `ml/.venv` environment.
- [ ] Data-processing libraries.
- [ ] ML libraries.
- [ ] Model storage/versioning.
- [ ] Experiment tracking if required.

The completed Python environment decision and the four pending technology decisions are intentionally treated separately.

---

## 1. Python Environment

**Decision:** Separate `ml/.venv` environment.

### Why

ML/data development has different dependency requirements from the backend runtime.

Separating the environments reduces dependency coupling and keeps ML experimentation independent from backend application dependencies.

### Current Environment

```text
ml/.venv
```

Configured Jupyter kernel:

```text
Nexora ML
```

### Current Position

Finalized.

**Status:** Pending.

### Selection Criteria

The final selection should consider:

- Models required by the project.
- Classification/regression requirements where applicable.
- Training and evaluation capabilities.
- Compatibility with the data-processing stack.
- Model serialization and loading support.

---

## 4. Model Storage / Versioning

**Status:** Pending.

### What This Decision Covers

Nexora will need a reliable way to store and identify trained model artifacts used for prediction.

The solution should make it possible to determine:

```text
Which model?
Which version?
Which training configuration?
Which artifact?
```

### Requirements

The eventual model-storage/versioning approach should support:

- Reproducible model artifacts.
- Clear model-version identification.
- Association between model versions and training configurations.
- Reliable model loading.
- Traceability between a prediction and the model version that produced it.
- Safe replacement of model versions.

### Decision Criteria

The approach should be evaluated based on:

- Project complexity.
- Number of models.
- Artifact size.
- Reproducibility requirements.
- Backend integration.
- Deployment requirements.
- Version-control suitability.

### Current Position

No final model-storage/versioning technology is selected yet.

---

## 5. Experiment Tracking

**Status:** Optional / Pending.

### What This Decision Covers

Experiment tracking may be useful when model development involves multiple experiments, configurations, metrics, datasets, and model artifacts.

Potential information to track includes:

- Experiment identifier.
- Model configuration.
- Hyperparameters.
- Dataset/version information.
- Evaluation metrics.
- Training results.
- Model artifacts.

### Decision Criteria

Experiment tracking should be introduced only if it provides meaningful value to the project's ML workflow.

It should be evaluated based on:

- Number of experiments.
- Model-development complexity.
- Reproducibility requirements.
- Artifact-management requirements.
- Additional infrastructure/maintenance cost.

### Current Position

Experiment tracking is not required to be selected at this stage.

It remains optional until the ML-development workflow demonstrates a practical need.

## 1. Decide Whether a Database Is Needed

**Status:** Pending.

### What This Decision Covers

A database should only be introduced if Nexora requires persistent application data.

Potential persistence requirements may include:

```text
Watchlist
Prediction / analysis history
User preferences
Application data
Other persistent state
```

### Decision Criteria

The requirement should be evaluated based on:

- Whether users need data to persist between sessions.
- Whether watchlists must be stored.
- Whether prediction history must be retained.
- Whether user preferences require persistence.
- Whether the application can operate using non-persistent or file-based storage during earlier stages.

### Current Position

A database has not yet been confirmed as mandatory.

The decision should follow the detailed application requirements.

**Status:** Pending.

If a database is required, the final technology should be selected after the persistence requirements are understood.

- Data-model complexity.
- Read/write requirements.
- Expected scale.
- Query requirements.
- Reliability.
- Development simplicity.
- Deployment environment.
- Maintenance requirements.
- Compatibility with the backend.

### Current Position

No database technology is finalized.

Potential entities may include:

### Definition Criteria

Each entity should be defined according to:

### Current Position

## 4. Define Retention Needs

**Status:** Pending.

Retention requirements define how long persistent data should remain available and when it should be archived or removed.

### Retention Questions

The final decision should answer:

- What data needs to be retained?
- How long should it remain available?

# Technology Selection Principles

All pending technology decisions should follow these principles.

## Fit for Purpose

Select technology according to actual Nexora requirements.

## Maintainability

Prefer technologies that can be understood, maintained, tested, and extended throughout the project.

## Compatibility

Selected technologies must work reliably with the surrounding project stack.

## Reproducibility

Dependencies, environments, models, and relevant configurations should be reproducible.

## Incremental Adoption

Do not introduce infrastructure or tooling before it provides practical value.

## Avoid Premature Decisions

A pending checklist item should remain pending until sufficient requirements and implementation context exist to make a justified decision.
