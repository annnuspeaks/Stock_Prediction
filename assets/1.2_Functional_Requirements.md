# Nexora --- Functional Requirements

## 1.2 Functional Requirements

This document defines the functional requirements for **Nexora --- AI
Stock Decision Support & Prediction Tool**.

These requirements describe what the product should allow users and
system components to do. Implementation technology, market-data provider
selection, detailed architecture, and deployment decisions are handled
in their respective later phases.

> **Scope principle:** Functional requirements define product behavior.
> They do not guarantee prediction accuracy, investment returns, or
> financial outcomes.

------------------------------------------------------------------------

## 1. Stock Search

Nexora shall allow users to search for a supported stock using an
appropriate identifier such as stock symbol or supported stock name.

The search should:

-   Accept a supported stock identifier or search term.
-   Return matching supported stocks.
-   Present sufficient information to distinguish matching stocks.
-   Handle an invalid or unsupported search gracefully.
-   Avoid presenting unavailable stocks as valid analysis targets.

**Initial decision:** Stock search is part of the core product workflow.

------------------------------------------------------------------------

## 2. Stock Selection

Nexora shall allow the user to select a stock from the available search
results or supported stock list.

After selection, the system should:

-   Store the selected stock context for the current analysis session.
-   Display the selected stock clearly.
-   Use the selected stock as the subject of subsequent data retrieval
    and prediction.
-   Prevent analysis from being requested without a valid stock
    selection.

**Initial decision:** Stock selection is mandatory before requesting an
analysis.

------------------------------------------------------------------------

## 3. User Preferences

Nexora shall support relevant user preferences where they improve the
analysis experience.

For the initial version, preferences should remain intentionally
lightweight rather than introducing unnecessary account/profile
complexity.

Initial preference scope:

-   Selected analysis/prediction horizon.
-   Optional risk preference where implemented.
-   User interface preferences may be added independently if required.

Preferences should not override system safety, data-quality,
model-validity, or risk rules.

**Initial decision:** User preferences are supported, but the first
version will keep them minimal and focused on analysis behavior.

------------------------------------------------------------------------

## 4. Time-Horizon Selection

Nexora shall allow the user to select the intended prediction/analysis
horizon.

The initial supported horizons are:

-   **1 trading day**
-   **1 trading week**

The selected horizon shall be passed through the analysis workflow and
reflected in the resulting prediction and explanation.

The system should clearly communicate the selected horizon in the
result.

**Initial decision:** The first version supports 1-day and 1-week
horizons. Additional horizons are future extensions.

------------------------------------------------------------------------

## 5. Risk Preference if Applicable

Nexora may allow the user to express a risk preference when the
implemented recommendation logic supports it.

For the initial product:

-   Risk preference is **optional**.
-   The system's own risk assessment remains active regardless of
    whether the user supplies a preference.
-   A user preference must not force a recommendation when evidence is
    insufficient.
-   A risk preference must not override data-quality checks or **NO
    SIGNAL** conditions.

A future implementation may use clearly defined categories such as
conservative, balanced, or growth-oriented, but the exact categories
should only be introduced when the recommendation/risk engine is ready
to support them consistently.

**Initial decision:** Risk preference is an optional enhancement; core
risk assessment is mandatory.

------------------------------------------------------------------------

## 6. Market-Data Retrieval

Nexora shall retrieve the market information required for the selected
stock and analysis horizon.

The retrieval workflow should:

-   Request the required data from the configured market-data provider.
-   Retrieve only data required by the applicable analysis workflow.
-   Respect provider availability, authentication, rate limits,
    freshness, and usage constraints.
-   Detect unsuccessful or incomplete retrieval.
-   Provide appropriate failure/no-data states to the user.

The specific primary and backup market-data providers will be selected
later after the provider evaluation required by the project checklist.

**Initial decision:** Market-data retrieval is a core backend
responsibility; provider selection remains a later
architecture/data-provider decision.

------------------------------------------------------------------------

## 7. Data Validation

Before analysis or prediction, Nexora shall validate the retrieved data.

Validation should include, where applicable:

-   Required fields are present.
-   Values are in expected formats and ranges.
-   Required historical coverage is available.
-   Data is sufficiently fresh for the requested analysis.
-   Missing, duplicated, malformed, or unusable records are detected.
-   Data quality problems do not silently proceed into prediction.

If the data fails required validation, Nexora should stop the affected
workflow or return an appropriate **NO SIGNAL**, stale-data, or error
state.

**Initial decision:** Data validation is mandatory before prediction.

------------------------------------------------------------------------

## 8. Data Processing

Nexora shall process validated market data into the representation
required by the prediction workflow.

Processing may include:

-   Cleaning.
-   Transformation.
-   Feature preparation.
-   Feature calculation.
-   Encoding or normalization where required by the selected model.
-   Alignment of data with the requested prediction horizon.

Processing logic should remain consistent with the preprocessing used
during model development.

The backend should not apply an undocumented or incompatible
transformation to model input.

**Initial decision:** Data processing is a required stage between
validation and prediction.

------------------------------------------------------------------------

## 9. Prediction

Nexora shall execute the applicable prediction workflow using validated
and processed data.

The prediction workflow should:

-   Load the appropriate model or model pipeline.
-   Use the selected stock and requested horizon.
-   Generate the applicable prediction output.
-   Return confidence/probability information where the model supports
    it.
-   Detect prediction failures.
-   Avoid presenting a prediction when required model/data conditions
    are not satisfied.

Predictions are estimates and shall not be presented as guaranteed
outcomes.

**Initial decision:** Prediction is a core product capability and
remains separate from final recommendation generation.

------------------------------------------------------------------------

## 10. Risk Assessment

Nexora shall assess relevant risk associated with the prediction where
the implemented risk layer supports the corresponding signals.

Risk assessment may consider factors such as:

-   Market volatility.
-   Model confidence.
-   Data quality.
-   Data freshness.
-   Market conditions.
-   Prediction uncertainty.
-   Other validated risk indicators introduced by the project.

The risk layer should be able to identify situations where a prediction
should not be converted into a strong recommendation.

**Initial decision:** Risk assessment is a required product stage and is
independent from the optional user risk preference.

------------------------------------------------------------------------

## 11. Recommendation Generation

Nexora shall generate a decision-support recommendation by combining
applicable prediction, risk, confidence, data-quality, and
rule/threshold information.

The initial supported recommendation outcomes are:

-   **BUY**
-   **SELL**
-   **WATCH**
-   **HOLD**
-   **NO SIGNAL**

The recommendation engine should:

-   Apply documented decision rules.
-   Consider risk and confidence where available.
-   Avoid forcing a recommendation when evidence is insufficient.
-   Preserve the distinction between model prediction and system
    recommendation.

**Initial decision:** Recommendation generation is a core system
capability.

------------------------------------------------------------------------

## 12. Recommendation Explanation

Nexora shall explain the generated recommendation in understandable
terms.

The explanation should communicate, where available:

-   The prediction.
-   The selected time horizon.
-   Relevant supporting signals.
-   Risk/confidence information.
-   Important data-quality considerations.
-   The main reason for the resulting recommendation.
-   Why **NO SIGNAL** was returned when applicable.

The explanation should not claim certainty or guaranteed financial
results.

**Initial decision:** Every user-facing recommendation should have an
understandable explanation or reason state.

------------------------------------------------------------------------

## 13. Result Visualization

Nexora shall present prediction and recommendation results through an
understandable user interface.

The result view should communicate, where applicable:

-   Selected stock.
-   Selected time horizon.
-   Prediction.
-   Recommendation.
-   Risk information.
-   Confidence/probability where available.
-   Supporting indicators/signals.
-   Explanation.
-   Relevant historical or market visualizations.

Visualizations should prioritize clarity over unnecessary complexity.

**Initial decision:** Result visualization is part of the core analysis
workflow.

------------------------------------------------------------------------

## 14. Watchlist

Nexora shall allow users to maintain a list of stocks they want to
monitor.

The initial watchlist functionality should support:

-   Adding a supported stock.
-   Removing a stock.
-   Viewing the current watchlist.
-   Selecting a watchlisted stock for analysis.

The watchlist should not imply automatic trading or automatic investment
action.

Persistence requirements and storage technology will be finalized during
the architecture/storage phase.

**Initial decision:** Watchlist is included in the product scope, with
implementation/storage details to be finalized later.

------------------------------------------------------------------------

## 15. Prediction History

Nexora shall allow users to review previous prediction results where
history storage is available.

A history entry should contain, where applicable:

-   Stock.
-   Analysis/prediction date and time.
-   Selected prediction horizon.
-   Prediction result.
-   Recommendation.
-   Risk/confidence information.
-   Relevant explanation or result summary.

History should represent what Nexora produced at that time and should
not be interpreted as a guarantee of future performance.

Persistence and retention details will be finalized during the
architecture/storage phase.

**Initial decision:** Prediction history is included in the product
scope; storage and retention implementation will be finalized later.

------------------------------------------------------------------------

## 16. Loading States

Nexora shall provide clear loading states for operations that may take
noticeable time.

Loading states should be supported for relevant stages such as:

-   Stock search.
-   Market-data retrieval.
-   Data processing.
-   Prediction.
-   Result loading.
-   Watchlist/history operations where applicable.

The interface should prevent confusing duplicate actions while an
operation is in progress where appropriate.

**Initial decision:** Loading states are required for all user-visible
asynchronous workflows.

------------------------------------------------------------------------

## 17. Error States

Nexora shall provide understandable error handling when an operation
cannot be completed.

Errors may occur because of:

-   Invalid user input.
-   Unsupported stock.
-   Market-data provider failure.
-   Network failure.
-   Authentication/configuration failure.
-   Invalid or insufficient data.
-   Prediction/model failure.
-   Backend/API failure.
-   Unexpected application errors.

The user-facing message should explain what happened at an appropriate
level and, where possible, indicate what the user can do next.

Technical details should be logged appropriately without exposing
secrets or unnecessary internal information to users.

**Initial decision:** Error handling is required across all major
workflows.

------------------------------------------------------------------------

## 18. No-Data / Stale-Data Handling

Nexora shall explicitly handle situations where required market data is
unavailable, incomplete, or stale.

The system should:

-   Detect missing data.
-   Detect data that exceeds the accepted freshness window.
-   Avoid silently using unusable data.
-   Clearly communicate the data problem.
-   Prevent misleading recommendations when data quality is
    insufficient.
-   Return **NO SIGNAL** where the product rules determine that a safe
    decision-support result cannot be produced.

**Initial decision:** No-data and stale-data handling is mandatory and
is part of the risk-aware design of Nexora.

------------------------------------------------------------------------

# Functional Workflow

The initial functional workflow is:

``` text
User
  ↓
Stock Search
  ↓
Stock Selection
  ↓
User Preferences / Time Horizon
  ↓
Market-Data Retrieval
  ↓
Data Validation
  ↓
Data Processing
  ↓
Prediction
  ↓
Risk Assessment
  ↓
Recommendation Generation
  ↓
Recommendation Explanation
  ↓
Result Visualization
  ↓
Watchlist / Prediction History
```

Exception paths are handled through:

``` text
Loading States
Error States
No-Data Handling
Stale-Data Handling
NO SIGNAL
```
