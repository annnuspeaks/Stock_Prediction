# 2.1 High-Level Architecture

## Purpose

This document defines the high-level architecture of **Nexora — AI Stock Decision Support & Prediction Tool**.

The purpose of this phase is to establish the major system components, their responsibilities, and the high-level flow between them before detailed implementation is expanded.

> **Important:** This is an architecture and documentation phase. It defines the blueprint for implementation; it is not itself a coding phase.

---

## Architecture Overview

Nexora follows a modular architecture in which the user interacts with the frontend, the frontend communicates with the backend/API, and the backend coordinates market-data retrieval, validation and processing, ML prediction, risk assessment, and decision-support logic.

High-level flow:

```text
User
  ↓
Frontend
  ↓
Backend / API
  ↓
Market Data
  ↓
Data Processing & Validation
  ↓
ML Prediction
  ↓
Decision / Risk Layer
  ↓
Prediction + Risk + Recommendation + Explanation
  ↓
Frontend Result UI
```

The architecture is intentionally modular so that additional prediction models, data providers, storage, and deployment capabilities can be introduced as the project evolves.

---

## 1. User

The **User** is the system's primary external actor.

The user interacts with Nexora through the frontend to:

- Search for a supported stock.
- Select a stock.
- Choose an analysis/prediction horizon.
- Provide applicable analysis preferences.
- Request an analysis.
- Review prediction results.
- Review risk and confidence information where supported.
- Understand the explanation behind the generated outcome.
- Manage a watchlist.
- Review prediction/analysis history.

The user remains responsible for the final investment decision.

Nexora is a decision-support and prediction tool and does not guarantee returns or provide personalized financial advice.

---

## 2. Frontend

The **Frontend** is the user-facing application layer.

### Technology

The current frontend technology decisions are:

```text
React + TypeScript
Vite
React Router
React Context + hooks initially
Recharts
Lucide React + custom Nexora UI components
CSS Modules + global CSS/design tokens
```

### Responsibilities

The frontend is responsible for:

- Stock search and selection.
- User input and analysis preferences.
- Time-horizon selection.
- Requesting analysis from the backend/API.
- Displaying loading states.
- Displaying errors and no-data/stale-data states.
- Presenting prediction results.
- Presenting risk/confidence information where supported.
- Presenting recommendations and explanations.
- Visualizing relevant results.
- Watchlist interaction.
- Prediction/analysis history interaction.

The frontend should not contain the core prediction logic. Prediction and decision-support processing should remain behind the backend/API boundary.

---

## 3. Backend / API

The **Backend/API** provides the application service layer between the frontend and the underlying data, processing, ML, and decision components.

### Technology

The current backend technology decisions are:

```text
Python
FastAPI
Pydantic
OpenAPI
Swagger UI
ReDoc
Python logging
Environment variables + .env + python-dotenv
```

### Responsibilities

The backend/API is responsible for:

- Receiving requests from the frontend.
- Validating request data.
- Coordinating market-data retrieval.
- Coordinating data validation and processing.
- Invoking the prediction layer.
- Coordinating risk assessment.
- Coordinating decision-support logic.
- Returning structured results to the frontend.
- Handling application-level errors.
- Providing API documentation.

The backend is the primary application orchestration boundary.

---

## 4. Market-Data Provider

The **Market-Data Provider** supplies the market information required by Nexora.

The initial project scope focuses on:

```text
Indian equity market
NSE/BSE-listed stocks
```

The final market-data provider has not yet been fixed.

The provider will be selected after considering:

- Market coverage.
- Data freshness.
- Historical-data availability.
- Reliability.
- Usage limits.
- Free/free-tier availability where applicable.
- Usage terms.

The selected provider should be accessed through the backend rather than directly from the frontend.

---

## 5. Data-Processing Layer

The **Data-Processing Layer** prepares incoming market information for analysis and prediction.

### Responsibilities

It is responsible for:

- Validating incoming data.
- Handling missing or invalid data.
- Handling stale data where applicable.
- Preparing data in a consistent format.
- Performing required transformations.
- Generating model-ready features.
- Maintaining consistent preprocessing between development and prediction.

High-level flow:

```text
Raw Market Data
      ↓
Validation
      ↓
Cleaning / Preparation
      ↓
Transformation
      ↓
Feature Preparation
      ↓
Model-Ready Data
```

The exact processing and feature-engineering techniques will be defined during the ML/data-development phases.

---

## 6. ML Prediction Layer

The **ML Prediction Layer** converts prepared data into model predictions.

### Responsibilities

It is responsible for:

- Loading the applicable trained model.
- Receiving model-ready features.
- Generating predictions.
- Providing confidence/probability information where supported.
- Supporting the defined prediction horizons.
- Returning structured prediction outputs to the application.

Initial prediction horizons:

```text
1 trading day
1 trading week
```

The detailed model architecture, algorithms, training process, evaluation, and model artifacts will be defined during the corresponding ML phases.

The ML layer should remain separated from frontend presentation logic and should be callable through a controlled application interface.

---

## 7. Decision / Risk Layer

The **Decision / Risk Layer** converts prediction information and relevant risk/context information into a decision-support outcome.

Possible outcomes are:

```text
BUY
SELL
WATCH
HOLD
NO SIGNAL
```

The decision should not be treated as a direct replacement for the raw model output.

High-level flow:

```text
Prediction
    +
Confidence
    +
Risk Assessment
    +
Data Quality
    +
Decision Rules
    ↓
Decision-Support Outcome
```

The system may return:

```text
NO SIGNAL
```

when the available evidence does not satisfy defined data-quality, confidence, or risk requirements.

The final decision rules will be refined as the prediction and risk components are implemented.

---

## 8. Database / Storage

A dedicated database is **not required to be finalized at this high-level architecture stage**.

Storage requirements will be determined based on the application's actual persistence needs, including areas such as:

- Watchlist data.
- Prediction/analysis history.
- User preferences where persistence is required.
- Application configuration.
- Other future application data.

The architecture therefore keeps storage as an extensible component rather than prematurely selecting a database technology.

High-level representation:

```text
Application
    ↓
Storage Layer
    ↓
Persistent Data
```

The final storage technology and schema will be decided when the corresponding application requirements are implemented.

---

## 9. Logging / Monitoring

Logging and monitoring support system reliability, debugging, and operational visibility.

### Current Logging Decision

The backend uses:

```text
Python logging
```

Logging should support appropriate information such as:

- Application events.
- API activity.
- Validation failures.
- Processing errors.
- Prediction-related errors.
- Unexpected exceptions.
- Important system state changes.

Sensitive information and secrets must not be written to logs.

### Monitoring

Detailed production monitoring is not yet implemented.

Monitoring and observability can be expanded as the application approaches deployment.

---

## 10. CI/CD Pipeline

Nexora currently has **Continuous Integration (CI)** implemented using GitHub Actions.

Current CI flow:

```text
Code Change
    ↓
Push / Pull Request
    ↓
GitHub Actions
    ↓
Project Structure Check
    ↓
Frontend Dependencies
    ↓
Frontend Checks
    ├── ESLint
    └── Production Build
    ↓
Backend Dependencies
    ↓
Backend Checks
    └── Python Compilation
    ↓
Automated Tests
    └── Pytest
    ↓
PASS / FAIL
```

The workflow is maintained at:

```text
.github/workflows/ci.yml
```

CI is triggered by:

```text
Push to main
Pull request targeting main
```

### Continuous Delivery / Deployment

CD is intentionally deferred.

Deployment will be introduced after:

- The application has a stable deployable build.
- A deployment target has been selected.
- Development/staging/production environments have been defined.
- Environment configuration has been defined.
- Deployment and rollback processes have been established.

Therefore:

```text
CI → Implemented
CD → Deferred
```

## Architecture Principles

The high-level architecture follows these principles:

### Separation of Concerns

Frontend, backend, data processing, ML prediction, decision/risk logic, and supporting infrastructure have distinct responsibilities.

### Modularity

Individual components should be replaceable or extendable without requiring unnecessary changes across the entire application.

### Backend-Controlled Data Access

External market-data services should be accessed through the backend rather than directly from the frontend.

### ML/Application Separation

Model development and prediction logic should remain separate from frontend presentation concerns.

### Explainability

The final result should distinguish between:

```text
Market Information
       ↓
Model Prediction
       ↓
Risk Assessment
       ↓
System Recommendation
       ↓
User's Final Decision
```

### Incremental Development

Architecture decisions should support the current project scope while allowing future expansion.
